# What 2.x carried forward from 1.x

The 2.0 release changed the toolchain: TypeScript, ESM, Vitest, a new dashboard, a config loader with schema-generated types and hot reload. The data model and the trust assumptions of 1.x are unchanged in 2.x. The table lists each retained assumption, its consequence in 2.x, and the v3 replacement.

| 1.x assumption retained in 2.x                                                                                         | Consequence                                                                                                                                                                      | v3                                                                                                                                                                        |
| ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The pusher is the committer of the last commit in the pack                                                             | Identity, push permission and the "cannot approve your own push" rule all rest on a line the client wrote                                                                        | The pusher is resolved from the credential on the connection. Commit metadata is recorded, optionally checked, never trusted ([Identity](./identity.md))                  |
| A push is identified by `commitFrom__commitTo`                                                                         | The same commits pushed to two repositories, or two branches, are one record. The id doubles as a filesystem path and as the approval lookup key                                 | Records have assigned opaque ids. Approvals are bound to repository, ref, range and pack digest, and are single-use ([Push lifecycle](./push-lifecycle.md))               |
| A user has one `email` and one untyped `gitAccount`                                                                    | A person with accounts on two hosts cannot be represented. Two users sharing an email is an error at push time. `gitAccount` is not indexed                                      | Users hold many emails, many provider-tagged SCM identities and many SSH keys, each with a verification source ([Data model](./data-model.md))                            |
| Repository access is two username arrays, `canPush` and `canAuthorise`, embedded in the repository document            | No groups, no patterns, no reviewer scoping, no audit of who granted what                                                                                                        | Capability-set grants on pattern targets, held directly or through groups, stored separately and audited ([Authorization](./authorization.md))                            |
| Roles are one `admin` boolean                                                                                          | Admin can do everything, including approve its own push                                                                                                                          | Roles are data; `admin` grants administration, not review or self-certification                                                                                           |
| Push state is a set of booleans (`blocked`, `error`, `authorised`, `canceled`, `rejected`) plus a waiting marker       | "Failed a check" and "awaiting review" derive from the same flag; the canonical state is a query-time inference                                                                  | Eight canonical states with a transition table enforced in one module ([Push lifecycle](./push-lifecycle.md))                                                             |
| A processor receives the Express request and a mutable action                                                          | Every transport must fake an HTTP request. SSH builds mock request and response objects to reach the chain. Plugins depend on Express                                            | Checks receive a read-only submission view and return a verdict. Both transports and both modes call the same engine ([Policy decision contract](./policy-contract.md))   |
| Three git mechanisms: a hand-written pkt-line and pack parser, `isomorphic-git` for cloning, spawned `git` for writing | Every new content check reads through the in-memory parser, which has no limits on inflated size, object count or line count                                                     | One engine: git itself with native quarantine, a bounded pkt-line reader for the command section, and content resolved against the mirror ([Git engine](./git-engine.md)) |
| The approval is consulted by looking up the push id                                                                    | Any push presenting the same commit range consumes the approval, in any repository, on any ref. The stored record replaces the live one, so the audit trail names the first push | The retry is matched on the full binding. The live record is never replaced                                                                                               |
| SSH public-key authentication accepts a key found in the user table                                                    | The signature the client sends over the session identifier is not checked                                                                                                        | The signature is verified before the fingerprint is looked up. The presented login is ignored                                                                             |
| Two Express apps, one for the proxy and one for the service, plus a CLI wrapping the service                           | Two ports, two sets of middleware, duplicated auth helpers                                                                                                                       | One process, one HTTP listener, one router tree ([Overview](./index.md))                                                                                                  |
| The storage interface is one object with 38 methods, implemented per engine                                            | Adding an entity means editing every sink. NeDB shapes every entity toward a denormalised document                                                                               | Narrow store interfaces per aggregate, an explicit index list per store, versioned migrations ([Data model](./data-model.md))                                             |
| The audit trail is the push record itself                                                                              | Transitions are reconstructed from timestamps on the record; a record that ended in error may have none                                                                          | An explicit event log per push, appended by the lifecycle module                                                                                                          |

## Kept from 2.x

- The configuration module: JSON schema, generated types, file, HTTP and git sources with merge semantics, reference documentation generated from the schema.
- Passport-based dashboard authentication with local, Active Directory and OIDC strategies.
- Plugin loading from file paths and npm modules.
- npm distribution and the Docusaurus site.
- Sideband progress to the client during evaluation.
- Vitest, ESLint with the license-header rule, Prettier, the CI matrix.

The dashboard is unchanged on this branch. It compiles against a copy of the 2.x API types under `src/ui/legacy` and will be re-pointed at the v3 API as a separate piece of work.
