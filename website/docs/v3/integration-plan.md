# Integration plan

How the v3 modules enter the 2.x tree without a flag day: each new layer is added beside the existing code, the existing code is pointed at it behind its current interface, and the old implementation is deleted once nothing calls it. The 2.x processor chain, `Action` object, service API, configuration and dashboard keep working at every step. Each step is one pull request with its own tests and a rollback that is a revert.

Steps 1 to 3 need no model agreement and no schema change. Steps 4 to 7 change stored shapes and each carries a migration. Steps 8 to 10 change contributor-facing contracts and warrant a major version.

## Rules while both coexist

- New code never imports from the 2.x module it replaces. The 2.x module calls the new one.
- The `Action` object is the seam. New layers produce it or consume it until step 8 retires it.
- Behaviour is pinned before each rewiring by a test that pushes a real pack through the old path and the new path and compares the resulting record. The captured fixtures under `test/git/fixtures` are the inputs.
- Configuration is additive. New limits get defaults equal to today's effective behaviour where one exists, and the old keys keep working through the deprecated-field mechanism the config loader already has.
- Deletion is its own commit, after the rewiring has shipped a release.
